# RepairFlow --- Full-stack Portfolio Project

> โปรเจกต์หลักสำหรับปั้น Portfolio ภายใน 12 สัปดาห์\
> บทบาทเป้าหมาย: Full-stack Developer ที่มี Product Thinking

## 1. แนวคิดโปรเจกต์

**RepairFlow** คือระบบ SaaS
สำหรับบริหารงานซ่อมและติดตามสถานะสำหรับร้านซ่อมอุปกรณ์อิเล็กทรอนิกส์ เช่น
ร้านซ่อมคอมพิวเตอร์และอุปกรณ์ไอทีที่มีช่างหลายคนและมีคลังอะไหล่

เป้าหมายไม่ใช่แค่สร้างเว็บไซต์ CRUD แต่สร้างระบบที่แก้ปัญหาการทำงานจริง
โดยครอบคลุมตั้งแต่รับงานซ่อม มอบหมายช่าง ประเมินราคา เบิกอะไหล่ ติดตามสถานะ
ไปจนถึงชำระเงินและดูรายงาน

### ปัญหาที่ระบบต้องแก้

-   ลูกค้าไม่ทราบว่างานซ่อมอยู่ในขั้นตอนใด
-   พนักงานไม่ทราบว่าใครเป็นผู้รับผิดชอบงาน
-   การเบิกอะไหล่ทำให้ยอดสต็อกไม่ตรงกับของจริง
-   มีการเสนอราคา แต่ยังไม่มีการอนุมัติจากลูกค้า
-   งานซ่อมเสร็จแล้วแต่ไม่มีการแจ้งลูกค้าอย่างเป็นระบบ
-   ผู้จัดการไม่เห็นภาพรวมของงานล่าช้า ระยะเวลาซ่อม และรายได้

## 2. กลุ่มผู้ใช้งานและบทบาท

  บทบาท             ความรับผิดชอบ
  ----------------- --------------------------------------------------
  Owner / Manager   ดูภาพรวมร้าน จัดการผู้ใช้ ดูรายงาน และตรวจสอบงาน
  Receptionist      รับอุปกรณ์ เปิดใบงาน บันทึกข้อมูลลูกค้า และเสนอราคา
  Technician        รับผิดชอบงานซ่อม อัปเดตสถานะ บันทึกผล และเบิกอะไหล่
  Customer          ติดตามสถานะ ตรวจสอบใบเสนอราคา และอนุมัติหรือปฏิเสธราคา

ต้องออกแบบ Authorization ที่ฝั่ง Backend เป็นหลัก ไม่พึ่งการซ่อนปุ่มใน Frontend
เพียงอย่างเดียว

## 3. ขอบเขตฟีเจอร์

### 3.1 Work Order Management

-   สร้างใบงานซ่อมและบันทึกข้อมูลอุปกรณ์
-   บันทึกอาการเสียและรูปภาพประกอบ
-   มอบหมายช่างผู้รับผิดชอบ
-   อัปเดตสถานะงานตาม Workflow
-   เก็บประวัติการเปลี่ยนสถานะ
-   ค้นหาและกรองงานตามสถานะ ช่าง วันที่ และลูกค้า

ตัวอย่างสถานะ:

`RECEIVED → DIAGNOSING → WAITING_FOR_APPROVAL → WAITING_FOR_PARTS → IN_PROGRESS → COMPLETED → DELIVERED`

สถานะจริงควรออกแบบตามกฎธุรกิจ และไม่อนุญาตให้เปลี่ยนข้ามขั้นตอนโดยไม่มีเงื่อนไขรองรับ

### 3.2 Parts & Inventory

-   จัดการรายการอะไหล่
-   รับอะไหล่เข้าคลัง
-   เบิกอะไหล่ไปใช้กับใบงาน
-   บันทึก Stock Movement ทุกครั้ง
-   ตรวจสอบยอดคงเหลือและประวัติการเคลื่อนไหว
-   ป้องกันการเบิกเกินจำนวนคงเหลือ

**กรณีทดสอบสำคัญ --- Concurrent Stock Deduction**

สมมติว่ามีอะไหล่เหลือ 1 ชิ้น และช่าง 2 คนพยายามเบิกพร้อมกัน
ระบบต้องรับประกันว่ามีเพียงหนึ่งคำขอที่สำเร็จ โดยใช้ Database Transaction
และกลไกควบคุม Concurrency ที่เหมาะสม

### 3.3 Quotation & Customer Approval

-   สร้างใบเสนอราคาจากค่าแรงและอะไหล่
-   ส่งให้ลูกค้าตรวจสอบ
-   ลูกค้าอนุมัติหรือปฏิเสธใบเสนอราคา
-   บันทึกประวัติการตัดสินใจ
-   ป้องกันการอนุมัติซ้ำหรืออนุมัติใบเสนอราคาที่หมดอายุ

### 3.4 Customer Portal

-   เข้าถึงข้อมูลด้วยบัญชีลูกค้า
-   ดูรายการอุปกรณ์และงานซ่อมของตนเอง
-   ติดตามสถานะและประวัติ
-   ตรวจสอบใบเสนอราคา
-   อนุมัติหรือปฏิเสธราคา

ลูกค้าต้องไม่สามารถเข้าถึงใบงานของลูกค้าคนอื่นได้ แม้จะพยายามเรียก API โดยตรง

### 3.5 Operations Dashboard

-   จำนวนงานซ่อมแยกตามสถานะ
-   งานที่เกินกำหนด
-   ระยะเวลาซ่อมเฉลี่ย
-   รายได้ตามช่วงเวลา
-   งานซ่อมที่ช่างแต่ละคนรับผิดชอบ

ตัวเลขใน Dashboard ต้องมาจากข้อมูลจริงและตรวจสอบย้อนกลับได้ ไม่ใช้ข้อมูล Mock
ในหน้ารายงานหลัก

### 3.6 Audit Log

บันทึกเหตุการณ์สำคัญ เช่น

-   ใครสร้างหรือแก้ไขใบงาน
-   ใครเปลี่ยนสถานะ
-   ใครอนุมัติใบเสนอราคา
-   ใครเบิกหรือรับอะไหล่
-   เกิดเหตุการณ์เมื่อใด

### Architecture Decision

เริ่มด้วย **Modular Monolith** ไม่เริ่มจาก Microservices
เพราะระบบยังมีขนาดเล็กและต้องการลดภาระการดูแลระบบ

แยกโมดูลตาม Domain เช่น:

-   `auth`
-   `users`
-   `customers`
-   `work-orders`
-   `quotations`
-   `inventory`
-   `payments`
-   `reports`
-   `audit-logs`

เพิ่ม Redis, Queue หรือบริการแยกเฉพาะเมื่อมีข้อกำหนดด้าน Performance หรือ
Background Processing ที่ชัดเจน

## 8. วิธีใช้ AI ระหว่างพัฒนา

เป้าหมายคือใช้ AI เพิ่มความเร็ว
โดยไม่ยกความรับผิดชอบในการตัดสินใจและตรวจสอบออกจากตัวเอง

1.  **กำหนดปัญหา:** Developer เป็นผู้กำหนดปัญหาและผลลัพธ์ที่ระบบต้องการ
2.  **สำรวจทางเลือก:** ให้ AI ช่วยเสนอ Schema, Architecture และ
    Implementation พร้อมข้อแลกเปลี่ยน
3.  **ตรวจสอบเหตุผล:** ตรวจ Business Rules, Database Transactions และ
    Authorization
4.  **พัฒนาและทดสอบ:** ให้ AI ช่วยเขียนโค้ดและ Test Cases
    แต่ต้องอ่านและตรวจสอบผล
5.  **ยืนยันด้วยการใช้งานจริง:** รันระบบ ทดสอบ Workflow
    และตรวจสอบข้อมูลที่เกิดขึ้นจริง

ไม่จำเป็นต้องเขียนโค้ดทุกบรรทัดด้วยตัวเอง แต่ต้องอธิบายได้ว่าโค้ดทำงานอย่างไร
ทำไมจึงเลือกวิธีนั้น และจะตรวจสอบความถูกต้องได้อย่างไร

## 9. Definition of Done

ฟีเจอร์หนึ่งจะถือว่าเสร็จเมื่อ:

-   [ ] ตรงตาม Acceptance Criteria
-   [ ] มีการตรวจสอบ Input ทั้ง Client และ Server ตามความเหมาะสม
-   [ ] มีการตรวจสอบ Authentication และ Authorization
-   [ ] Business Rules ทำงานถูกต้อง
-   [ ] รองรับ Error Cases ที่สำคัญ
-   [ ] มี Automated Tests ตามระดับความเสี่ยง
-   [ ] ทดสอบ Workflow จริงแล้ว
-   [ ] ตรวจสอบผลกระทบต่อข้อมูลที่เกี่ยวข้องแล้ว
-   [ ] มีเอกสารหรือคำอธิบายที่จำเป็น
-   [ ] Deploy แล้วและตรวจสอบบน Environment เป้าหมายแล้ว

## 10. เป้าหมายเมื่อเรียนจบ

สามารถนำเสนอโปรเจกต์นี้ในการสัมภาษณ์ได้ว่า:

> ผมสามารถเริ่มจากการวิเคราะห์ปัญหาทางธุรกิจ ออกแบบ Data Model และ API พัฒนา
> Frontend และ Backend จัดการ Business Logic ที่มีความซับซ้อน ทดสอบความถูกต้อง
> และ Deploy ระบบให้ใช้งานได้จริง โดยใช้ AI เป็นเครื่องมือช่วยพัฒนา
> ไม่ใช่เป็นผู้ตัดสินใจแทนทั้งหมด

**เป้าหมายไม่ใช่การสร้างระบบที่ใหญ่ที่สุดภายใน 3 เดือน
แต่คือการสร้างระบบที่เข้าใจลึกที่สุดในขอบเขตที่เหมาะสม**
